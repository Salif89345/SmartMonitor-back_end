# 1. Statut de clôture

**SM-072 - Broker distant et TLS : VALIDÉ**

Date de clôture : **23 août 2026**  
Périmètre validé : **SM-072-1 à SM-072-9 inclus**  
Environnement de validation : **SmartMonitor-Lab / DEV**

La clôture de SM-072 confirme que SmartMonitor ne dépend plus du broker Mosquitto local pour son fonctionnement vertical réel. Le firmware ESP32 et le backend FastAPI se connectent au broker EMQX Cloud via MQTT sur TLS, avec authentification distincte, ACL restrictives, reconnexion automatique, statut online/offline observable et chaîne commande/réponse démontrée depuis l'application mobile jusqu'au device puis retour vers l'application.

Le critère essentiel est donc atteint : **le backend et le firmware communiquent réellement à travers un broker Internet distant en TLS, avec ACL vérifiées, sans dépendance fonctionnelle au broker local.**

---

# 2. Objet et périmètre de SM-072

SM-072 avait pour objectif de faire évoluer l'architecture MQTT SmartMonitor depuis un environnement de développement local vers une infrastructure distante exploitable pour l'accès Internet et compatible avec la future architecture de production.

Le périmètre traité couvre :

1. l'audit de l'architecture MQTT existante ;
2. le choix d'un broker Internet ;
3. le déploiement du broker distant ;
4. le chiffrement MQTT par TLS sur le port 8883 ;
5. l'authentification et les ACL ;
6. la connexion du backend au broker distant ;
7. la connexion du firmware ESP32 au broker distant ;
8. les mécanismes de reconnexion, supervision et observabilité ;
9. la validation verticale réelle hors broker local, jusqu'à l'application mobile.

SM-072 ne redéfinit pas le contrat MQTT métier de SmartMonitor. Il s'appuie sur les choix de protocole et d'architecture déjà établis, notamment le principe :

```text
Application mobile
      |
      | API HTTP/HTTPS
      v
Backend SmartMonitor
      |
      | MQTT / TLS 8883
      v
EMQX Cloud
      |
      | MQTT / TLS 8883
      v
SmartMonitor ESP32
```

L'application mobile **ne se connecte jamais directement au broker MQTT**. Le backend reste l'unique passerelle métier entre l'application et les appareils.

---

# 3. Situation de départ

Avant SM-072, la chaîne MQTT de développement reposait principalement sur un broker Mosquitto local accessible sur le réseau LAN du poste de développement.

Référence historique :

```text
Broker local : 192.168.1.208:1883
Transport    : MQTT TCP local
Broker       : Mosquitto
```

Cette architecture était suffisante pour développer et tester le protocole MQTT, les topics, les commandes et les réponses, mais elle ne permettait pas de valider l'accès distant réel ni le comportement du système lorsqu'aucun broker local n'était disponible.

Les risques identifiés lors de l'audit étaient notamment :

- dépendance au PC de développement ;
- absence de chiffrement MQTT sur le chemin local historique ;
- absence d'authentification/ACL de niveau cloud ;
- impossibilité de tester un parcours Internet réaliste ;
- impossibilité de distinguer clairement les droits du backend et ceux d'un device ;
- absence de preuve que la reconnexion fonctionnait avec un broker distant ;
- absence de preuve verticale complète application -> backend -> cloud -> ESP32 -> cloud -> backend -> application.

# 4. Architecture cible retenue

L'architecture retenue après SM-072 est :

```text
+------------------------+
| Application SmartMonitor|
| Flutter / smartphone    |
+-----------+------------+
            |
            | API SmartMonitor
            | HTTP en DEV LAN / HTTPS cible
            v
+------------------------+
| Backend FastAPI         |
| smartmonitor-backend-v1 |
+-----------+------------+
            |
            | MQTT 3.1.1
            | TLS / TCP 8883
            v
+-----------------------------+
| EMQX Cloud Serverless       |
| SmartMonitor-Lab            |
| Broker Internet distant     |
+-------------+---------------+
              |
              | MQTT 3.1.1
              | TLS / TCP 8883
              v
+-----------------------------+
| SmartMonitor ESP32          |
| client ID unique            |
+-----------------------------+
```

Cette architecture respecte la séparation déjà décidée dans la plateforme SmartMonitor :

- **l'application parle à l'API** ;
- **le backend applique les droits métier et pilote MQTT** ;
- **EMQX assure le transport, l'authentification, les ACL, les sessions et le routage MQTT** ;
- **l'ESP32 publie son état et exécute les commandes qui lui sont adressées**.

# 5. SM-072-1 - Audit de l'architecture MQTT actuelle et cible

**Statut : VALIDÉ**

L'audit a confirmé que le contrat MQTT existant pouvait être conservé lors du passage au cloud. Les quatre topics principaux par appareil restent :

```text
smartmonitor/<device_id>/state
smartmonitor/<device_id>/command
smartmonitor/<device_id>/status
smartmonitor/<device_id>/response
```

Un topic de provisioning utilisé par l'association existe également :

```text
smartmonitor/provisioning/<device_uid>/claim-proof
```

Le passage au broker distant n'a donc pas nécessité de casser le modèle métier. Il a principalement consisté à remplacer le transport local par une connexion Internet TLS authentifiée et contrôlée par ACL.

Décision structurante : **conserver l'application totalement découplée de MQTT**. Cela évite d'exposer au smartphone les identifiants du broker, les topics techniques et les permissions de transport.

# 8. SM-072-4 - TLS 8883 et gestion des certificats

**Statut : VALIDÉ**

## 8.1 Backend

Le backend active TLS via Paho MQTT lorsque `MQTT_TLS_ENABLED` est vrai. Le certificat d'autorité est fourni par configuration externe :

```text
MQTT_TLS_ENABLED=true
MQTT_CA_CERT_PATH=C:\Dev\SmartMonitor_Backend\certs\emqxsl-ca.crt
```

Le code backend utilise :

```python
client.tls_set(ca_certs=MQTT_CA_CERT_PATH)
```

Les identifiants sensibles restent dans l'environnement de configuration et ne sont pas intégrés à cette documentation.

## 8.2 Firmware ESP32

Le firmware utilise un client TLS (`WiFiClientSecure`) et une autorité de certification intégrée au firmware dans le fichier de certificats MQTT. La chaîne validée utilise la CA publique correspondante au certificat présenté par le broker.

Le firmware attend également une heure NTP plausible avant de lancer la connexion TLS. Ce point est important : la validation temporelle d'un certificat TLS ne peut pas être considérée fiable avec une horloge système initialisée à une date incorrecte.

Séquence observée au démarrage :

```text
Wi-Fi connecté
-> démarrage NTP
-> synchronisation NTP réussie
-> connexion MQTT TLS au broker distant
```

Le port utilisé est **8883**.

# 9. SM-072-5 - Authentification MQTT et ACL

**Statut : VALIDÉ**

Deux identités MQTT distinctes sont utilisées en DEV :

```text
Backend : smartmonitor-backend-dev
Device  : smartmonitor-device-dev
```

Aucun mot de passe n'est archivé dans ce document.

Le principe d'ACL retenu est le moindre privilège :

| Flux | Backend | Device |
|---|---|---|
| Publier `smartmonitor/+/command` | Autorisé | Refusé |
| Souscrire `smartmonitor/+/command` | Refusé | Autorisé |
| Publier `smartmonitor/+/state` | Refusé | Autorisé |
| Souscrire `smartmonitor/+/state` | Autorisé | Refusé |
| Publier `smartmonitor/+/status` | Refusé | Autorisé |
| Souscrire `smartmonitor/+/status` | Autorisé | Refusé |
| Publier `smartmonitor/+/response` | Refusé | Autorisé |
| Souscrire `smartmonitor/+/response` | Autorisé | Refusé |
| Claim proof de provisioning | Device publie | Backend souscrit |

Une règle de refus globale sur `#` est utilisée comme garde-fou final afin que ce qui n'est pas explicitement autorisé reste interdit.

Le résultat recherché est atteint : **le backend ne peut pas se comporter comme un device et un device ne peut pas se comporter comme le backend.**

# 10. SM-072-6 - Connexion du backend au broker distant

**Statut : VALIDÉ**

Le backend FastAPI utilise Paho MQTT 3.1.1 avec :

- `MQTT_HOST` configurable ;
- `MQTT_PORT` configurable ;
- authentification username/password ;
- TLS configurable ;
- certificat CA externe ;
- Client ID fixe du backend ;
- reconnexion automatique Paho ;
- resouscription après reconnexion.

Abonnements backend :

```text
smartmonitor/+/state
smartmonitor/+/status
smartmonitor/+/response
smartmonitor/provisioning/+/claim-proof
```

Après reconnexion, le backend efface son cache local de statuts device puis le reconstruit à partir des messages `/status`, notamment des retained messages. Cela évite de conserver artificiellement un état online qui daterait d'avant une coupure de session du backend.

Le healthcheck MQTT a été vérifié avec :

```text
GET /api/v1/health/mqtt
-> 200 OK
-> mqtt.connected = true
```

**Statut : VALIDÉ**

Le firmware ESP32 a été connecté à EMQX Cloud avec :

# 12. SM-072-8 - Reconnexion, supervision et observabilité

**Statut : VALIDÉ**

SM-072-8 a été validé par des coupures réelles et non par simple inspection statique.

## 12.1 Reconnexion ESP32

Une perte Wi-Fi a été provoquée. Le firmware a correctement :

1. détecté la perte Wi-Fi ;
2. marqué MQTT comme déconnecté ;
3. relancé la connexion Wi-Fi ;
4. resynchronisé le chemin réseau ;
5. reconnecté MQTT sur EMQX Cloud ;
6. resouscrit au topic `command` ;
7. republié `online` ;
8. repris les publications de télémétrie.

Le firmware applique un délai minimal entre deux tentatives MQTT afin d'éviter une boucle de reconnexion agressive.

## 12.2 Reconnexion backend

Le backend utilise :

```python
client.reconnect_delay_set(min_delay=1, max_delay=30)
```

La reconnexion du backend au broker distant et la resouscription aux quatre familles de topics ont été observées.

## 12.3 Last Will and Testament

Le device déclare un LWT :

```text
Topic   : smartmonitor/<device_id>/status
Payload : offline
Retained: true
QoS     : 0
```

Lors d'une coupure brutale de l'ESP32, le backend a reçu le statut `offline` puis, après redémarrage et reconnexion, le statut `online`.

Des événements `device_offline` puis `device_online` ont été enregistrés côté backend.

## 12.4 Observabilité EMQX

Le monitoring EMQX a permis de confirmer les sessions réelles du backend et de l'ESP32, leurs comptes, leurs Client IDs et leurs keepalives respectifs.

# 17. Règles MQTT importantes conservées

## 17.1 Status

Le topic `/status` est utilisé pour la présence :

- `online` publié par le device lorsqu'il est réellement prêt ;
- `offline` publié par LWT si le device disparaît brutalement ;
- message retained afin qu'un backend fraîchement reconnecté puisse reconstruire l'état courant.

## 17.2 Commandes

Le backend génère un `request_id`, publie la commande, puis attend une réponse associée.

Le backend refuse une réponse qui :

- n'est pas un objet JSON valide ;
- n'a pas le `request_id` attendu ;
- ne vient pas du topic `/response` attendu ;
- ne contient pas un `result` `ack` ou `nack` valide.

Cette corrélation empêche qu'une ancienne réponse ou la réponse d'un autre appareil soit assimilée à la commande en cours.

## 17.3 Réponses

Le firmware renvoie un document normalisé :

```text
schema_version
request_id
result = ack | nack
error_code
message
data
```

Une réponse de commande n'est pas retained.

# 18. Sécurité obtenue à l'issue de SM-072

SM-072 apporte les protections suivantes au chemin MQTT :

- chiffrement TLS sur le transport Internet ;
- vérification de l'autorité de certification ;
- identités MQTT séparées backend/device ;
- mots de passe non documentés dans l'archive ;
- séparation claire des droits publish/subscribe ;
- règle de refus par défaut ;
- application mobile sans accès direct au broker ;
- backend seul autorisé à transformer une action utilisateur en commande MQTT ;
- LWT/retained status pour éviter des états de disponibilité incohérents ;
- corrélation des commandes par `request_id`.

Ces mesures constituent une infrastructure DEV sérieuse et directement exploitable pour la suite du projet. Elles ne remplacent pas l'audit de cybersécurité final prévu dans la roadmap.

# Annexe B - Règle de maintenance documentaire

Toute évolution future de l'infrastructure MQTT devra préserver au minimum les invariants suivants :

- l'application ne reçoit pas d'identifiants MQTT ;
- MQTT Internet reste chiffré ;
- le backend et les devices conservent des identités distinctes ;
- les ACL suivent le moindre privilège ;
- `/status` reste cohérent avec la capacité réelle du device à recevoir une commande ;
- les réponses de commande restent corrélées par `request_id` ;
- une reconnexion ne doit pas conserver artificiellement un ancien état online ;
- un test de validation ne doit être déclaré `VALIDÉ` qu'après preuve réelle de bout en bout selon ses critères d'acceptation.
